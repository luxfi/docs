ZAP (**Z**ero-copy **A**pplication **P**rotocol) is a high-performance binary protocol for inter-process messaging on the Lux network. It provides 17x faster serialization and 11x less memory than MCP JSON-RPC while maintaining compatibility with existing MCP tools.

```go
import "github.com/luxfi/zap"
```

<Callout>
This page is the **arena codec** — the 16-byte-header format `luxfi/zap`
encodes. Three other layers also answer to the name ZAP, including one whose
header is five big-endian bytes and shares nothing with this one. See
[the ZAP family](/zap/family) before assuming which is meant.
</Callout>

## Performance

| Metric | MCP JSON-RPC | ZAP | Improvement |
|--------|--------------|-----|-------------|
| Serialization | 5,579 ns/op | 322 ns/op | 17x faster |
| Memory/call | 2,826 bytes | 256 bytes | 11x less |
| Allocations | 58/op | 2/op | 29x fewer |
| Parse time | ~1,000 ns | 2.9 ns | 345x faster |

## Wire format

Every message is a 16-byte header followed by a variable-length data segment.
All multi-byte integers are little-endian, and an offset is relative to the
position of the offset field itself. Data segments are 8-byte aligned.

```
Header (16 bytes)
  Magic        "ZAP\x00"                        bytes  0..4
  Version      2 (see below)                    bytes  4..6
  Flags        compressed / encrypted / signed  bytes  6..8
  Root offset  offset to the root object        bytes  8..12
  Size         total message size               bytes 12..16
Data segment (variable)
  Structs, lists, text, bytes...
```

### The version word

Two schemas are defined, and the number is a **schema** discriminator, not a
release number:

| Value | Schema |
|---|---|
| `1` | Legacy platform-chain schema — `NetworkID` at byte 0, no transaction-kind discriminator |
| `2` | Current schema — transaction kind at byte 0, every other field shifted by one |

Go's builder **emits `2`** and its reader **accepts `1` and `2`**. The overlap
is not free: a version-1-shaped transaction with `NetworkID = 11` has `0x0B` at
byte 0, which is also a valid transaction-kind value, so a version-1 header over
version-2 bytes would pass a discriminator check and then misread the rest of
the buffer. Wrapping code requires version 2.

A reader is widened before an emitter is flipped, never the other way round:
every reader in the fleet must accept the new value before the first writer
produces it. Rust (`hanzo-zap`) emits `1` today for exactly this reason — one
reader has not been widened yet — and its handshake bytes therefore differ from
Go's in one 16-bit word. That difference is [recorded in the corpus](/conformance)
as a known, deliberate divergence rather than hidden behind a passing test.

### What a decoder must refuse

Refusal is part of the protocol. Accepting a frame the network rejects is not
leniency, it is a second protocol — one peer admits a message the rest of the
network will not, and the two see different histories.

Go's reader enforces three rules and a conformant decoder enforces all three:

1. The magic is exactly `ZAP\0`.
2. The version is `1` or `2`.
3. The declared size at bytes 12..16 is **at least** the 16-byte header and **at
   most** the number of bytes actually present. The message is then truncated to
   that declared size.

Rule 3 is the one that gets left out, because a decoder that checks only magic
and version still reads every well-formed message correctly, and every test
written from the happy path passes. What it also does is read past the end of a
short frame and return values Go never saw. That is a **state** divergence, not
a transport one: these are the bytes transactions and predicate results are
decoded from, so the two nodes do not fail to talk — they agree on different
data.

The corpus records Go's verdict for each malformed frame, so a decoder can be
held to all three rules rather than to the two that are easy to remember. If
you are writing one, that is the check to run first.

## TLS Support

ZAP supports optional TLS via `NodeConfig.TLS`. When running on Go 1.26+, TLS connections default to **PQ-TLS 1.3** with ML-KEM-768 + X25519 hybrid key exchange -- no additional configuration required.

```go
node := zap.NewNode(zap.NodeConfig{
    NodeID:      "node-1",
    ServiceType: "_luxd._tcp",
    Port:        9651,
    TLS:         tlsConfig, // *tls.Config; Go 1.26 defaults to ML-KEM-768
})
```

Zero-copy semantics are preserved under TLS. The TLS layer operates on the same buffer without additional heap allocations.

## Port

`9999` is ZAP the way `80` is HTTP and `443` is HTTPS. Every ZAP-hosting service
binds it; the DNS name says which service answers.

## Use cases

- **AI agent orchestration**: 20-tool orchestrator runs at 150K ops/sec vs 10K with JSON-RPC
- **VM-to-VM communication**: cross-VM message routing on the Lux network
- **GPU cluster / FHE kernels**: zero-copy ciphertext transfer between compute nodes
- **Consensus**: 5-node consensus reaching agreement in ~450 microseconds
- **MCP bridge**: auto-discover and accelerate existing MCP servers with ZAP transport

| TypeScript | `@zap-proto/zap` | Reader and writer. |
| C++ | — | None. A C++ service speaks the [frame RPC](/zap/family) instead. |

A decoder is conformant when it agrees with [the corpus](/conformance) — which
records the bytes Go writes **and** the malformed frames Go refuses — not when
it round-trips its own output. Round-tripping your own output only proves the
encoder and decoder were written by the same person.
